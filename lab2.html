Lab 2: A Skill and Three Verification Drills

Download the starter pack (zip) Slides Agenda

Lab 2 has two parts. In Part A (about 25 minutes, after a short demo) you turn the pipeline you built in Lab 1 into a skill: a written procedure Claude loads by itself when a request matches it, so you never have to explain the pipeline again. In Part B (25 minutes) you run three short drills that check whether your project is safe to share and whether your results hold up for a reader who did not see you build them.

You need two files from the starter pack: SKILL_skeleton.md for Part A and lab2_verification_drills.md for Part B.

NoteWhat you will have at the end

When the lab is done, you should have:

  • A skill file, .claude/skills/fsds-panel/SKILL.md, in your Lab 1 folder. You tested it in a new session with a request that does not mention the skill by name.
  • The output of both credential-audit checks, saved in VERIFY_NOTES.md.
  • A referee report in ~/referee_room/review/ with three objections. It comes from a session that saw only your write-up.
  • One deny rule in .claude/settings.json, and a note on what happened when you tested it.

Demo 2: EDGAR text to data

Before Part A, I show a five-minute demo that applies the same steps to text. Claude pulls the Risk Factors section (Item 1A) from a set of 10-Ks on EDGAR and counts a keyword in each one. Two details are worth copying in your own work. Every downloaded filing is cached, so a rerun fetches nothing it already has. And the pipeline writes a quality report that says how many sections it extracted and gives a reason for every one it missed. A count of successes without reasons for the failures doesn’t tell you whether to trust the measure.

Part A: turn your pipeline into a skill

A skill is a folder holding a SKILL.md file. The file starts with a short header (the frontmatter) with a name and a description, followed by the steps of the procedure. Claude reads the description of every installed skill at the start of a session and loads the full steps only when a request matches it. So the description decides whether the skill ever runs.

Most first skills fail in the same way: the description reads as a title. Compare:

---
name: fsds-panel
description: FSDS data tool
---
---
name: fsds-panel
description: Use when the user asks to build a firm-year panel or a financial
  ratio from SEC Financial Statement Data Sets (FSDS), mentions sub.txt or
  num.txt, or asks for a median of an XBRL tag by year or industry.
---

The first says what the skill is. The second describes what a real request looks like, so Claude has something to match.

Build it.

  1. In your Lab 1 folder, make the skill folder at project scope, so it travels with this project:

    cd ~/stanford_lab && mkdir -p .claude/skills/fsds-panel

  2. Copy SKILL_skeleton.md from the starter pack to .claude/skills/fsds-panel/SKILL.md.

  3. In your Lab 1 session (or a new one in the same folder), ask Claude to fill in the skeleton from what you actually did: the inputs (which quarters, which tags, which aggregation), the steps in order, the filters, the paper-trail files, and the checks. Ask it to keep the steps general enough to work for a different tag.

  4. Read the result. Rewrite the description yourself if it reads like a title. List the phrases a real request would use.

  5. Make sure --- is on line 1 of the file, with no comment or blank line above it. Claude reads the frontmatter only when the file starts with it. Delete any leftover comments from the skeleton.

Test it. Don’t test in the session where you wrote the skill. That session already knows the pipeline, so it will do the work whether or not the skill fires.

  1. Leave Claude (type /exit) and start a fresh session in the same folder with claude.
  2. Ask for something the skill should handle without naming it, for a measure you did not build in Lab 1. For example: “What was the median ratio of long-term debt to total assets by fiscal year in the FSDS quarters in fsds/?”
  3. Watch the transcript. If the skill fires, Claude says it is using the fsds-panel skill. If instead it starts reading your Lab 1 scripts or asking how the files are laid out, the skill did not fire. Rewrite the description and test again in another fresh session.
  4. Confirm that the run follows your steps: the consolidated filter, DATA_PROFILE.md before any figure, and the paper trail.

You can always run a skill on purpose by typing /fsds-panel. That doesn’t test the description, so do the test above first.

Part B: three verification drills

Run all three on your own project. If you have a research repository on your laptop, use it for Drill 1, because that is where an exposed key would actually hurt you. Otherwise use ~/stanford_lab. Drill 1 needs a git repository. If your Lab 1 folder isn’t one yet, run git init and echo "fsds/" > .gitignore there, then ask Claude to commit your scripts.

Drill 1: the two-check credential audit

These two checks come from the full course’s Module 5, adapted for public data and API keys. Run both from the root of the repository. Both should come back empty. Paste both outputs into VERIFY_NOTES.md in the repo.

Check 1: has a credential file ever been committed?

git log --all --full-history --oneline -- '*.env' '*.env.*' '.mcp.json'

Expected output: nothing.

This looks for a .env file, or a variant such as .env.local, in any folder and at any point in the history, plus a project-level .mcp.json, which holds credentials if you ever registered an MCP server with project scope. If it returns even one commit, a credential file was committed at some point. Deleting the file now does not remove it from history. Anyone who clones the repo, including a coauthor, a referee running a replication package or a stranger on GitHub, can still find it in an old commit with git show <commit>:<path>.

Check 2: does your actual key appear anywhere?

In the full course this check searches for your WRDS password. This session uses no WRDS, so run it for each secret this project actually uses, such as an Anthropic or OpenAI API key or a GitHub token. Type read -s SECRET, paste the key (it won’t echo), and run the two searches with $SECRET:

read -s SECRET
git log --all --oneline -S"$SECRET"
git grep -l -F --untracked -e "$SECRET"

Expected output: nothing.

  • git log -S lists every commit that ever added or removed the key, including in a script you have since deleted.
  • git grep lists files git would pick up that contain it now. It skips gitignored files.

Both searches print commit IDs or file names, never the key. They look for the key itself, not the name of the variable that holds it, so a script that reads the key from the environment (the right way) passes, and a script with the key typed into it fails. Do not use a plain grep -r "API_KEY" . instead: it flags correct code and misses a key that was committed and later deleted.

If the project uses no secrets at all, run Check 1 and write “no secrets in this project” in VERIFY_NOTES.md for Check 2.

WarningIf either check finds something
  1. Treat the credential as compromised right away. Do not assume it is fine because no one saw it. Assume any credential that has ever been committed to a git repository is exposed, even in a private repo and even if you never pushed it anywhere.
  2. Revoke and rotate first, clean up second. Regenerate the API key (or change the password) before you touch the repository. If you clean the repo first and rotate later, the exposed credential stays valid while you work.
  3. Remove it from history, not just the current version. Deleting the current copy is not enough while the secret is still reachable in git log history. A history rewrite with git filter-repo or BFG removes it. If the project is small and early, starting a fresh repository is simpler.
  4. Confirm the fix by re-running both checks and getting a clean result before you consider the audit passed.

Drill 2: a clean-room referee

A session that watched you build the pipeline has heard all your reasons and tends to accept them. A referee has heard none of them. So give the review its own room: a fresh session in an empty folder that holds only what a reader of your paper would see, plus a deny rule that stops the session from editing it.

  1. In ~/stanford_lab, write summary.md yourself, in about five minutes and without the agent. Include the figure caption, a short paragraph on how the sample was built (files, filters, tags and your tag choice), and the attrition table. Leave out DECISIONS.md and your scripts. A referee gets the paper, not your notes.

  2. Build the room and start a fresh session in it. Replace my_figure.png with the name of your figure:

    mkdir -p ~/referee_room/paper ~/referee_room/.claude
cp ~/stanford_lab/summary.md ~/referee_room/paper/
cp ~/stanford_lab/my_figure.png ~/referee_room/paper/
echo '{"permissions":{"deny":["Edit(./paper/**)"]}}' > ~/referee_room/.claude/settings.json
cd ~/referee_room && claude

  3. Send this prompt:

    You are refereeing a short empirical exhibit for an accounting journal. You
have only what is in paper/. Do not edit any file. Read the caption, the
sample description and the attrition table, and look at the figure. Write
the three most serious objections to review/referee.md, most serious first.
For each, say what claim it undermines and what evidence would answer it.
Check whether the stated filters can produce the N in the attrition table.
Aim the criticism at the exhibit, not the author.

  4. Read review/referee.md. In VERIFY_NOTES.md, write down one objection you had stopped seeing. Then answer one objection in writing at the bottom of review/referee.md, not in the chat. In the chat, the model tends to give in.

Your personal ~/.claude/CLAUDE.md, if you have one, still loads in this room, so keep project details out of it. If the report is mostly praise, ask again for the three most serious problems.

Drill 3: one deny rule, tested

A line in CLAUDE.md saying “never change the raw data” is a request. Claude usually follows it, but nothing enforces it. A deny rule in .claude/settings.json is enforced: Claude Code refuses the matching action in every permission mode.

  1. In ~/stanford_lab, create .claude/settings.json (or add to it if it exists):

    {
  "permissions": {
    "deny": [
      "Edit(./fsds/**)",
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

  2. Record a fingerprint of one raw file: shasum fsds/2024q1/readme.htm

  3. Start a fresh session in the folder so the rules load (/exit, then claude). Run /permissions and check that the three rules are listed.

  4. Ask: “Append the line ‘test’ to fsds/2024q1/readme.htm with your file edit tool. Then try a shell command, echo test >> fsds/2024q1/readme.htm. Quote any error you get.” Both attempts should be refused.

  5. Run shasum fsds/2024q1/readme.htm again. It must match step 2. Paste the refusal text and both fingerprints into VERIFY_NOTES.md.

  6. Commit .claude/settings.json, so anyone who works in the repo gets the same rules.

Know the limit. The rule blocks Claude’s file tools and shell commands that name the path. It does not stop a Python script that opens the file itself. Only an operating-system sandbox (/sandbox, or a container) blocks that.
